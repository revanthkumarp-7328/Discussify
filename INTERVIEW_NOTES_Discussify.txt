DISCUSSIFY – INTERVIEW EXPLANATION NOTES (MERN)

1) 30-SECOND INTRO (ELEVATOR PITCH)
- Discussify is a MERN-based community discussion platform.
- Users can create/join communities, start discussions with attachments, share learning resources, and message other users in real-time.
- It includes authentication (JWT), role-based admin access, notifications, and Socket.IO for real-time messaging and online status.

2) PROBLEM STATEMENT / WHY I BUILT IT
- People need a single place to:
  - organize into topic communities
  - discuss posts with replies/likes
  - share curated resources (files/links)
  - communicate directly via chat
- Goal: build a scalable full-stack app with secure auth, clean API design, and real-time features.

3) TECH STACK (WHAT + WHY)
- Frontend: React 18 + React Router + Material UI (MUI)
  - clean UI components + faster development
  - client-side routing and protected routes
- Backend: Node.js + Express
  - REST APIs, middleware, validation
- Database: MongoDB + Mongoose
  - flexible schema for communities, discussions, nested replies/comments
- Auth/Security:
  - JWT auth (Authorization: Bearer <token>)
  - bcrypt password hashing
  - helmet + rate limiting + CORS
- Real-time:
  - Socket.IO (messages, online status, community room updates)
- File upload:
  - multer (uploads to /uploads/* folders)

4) HIGH-LEVEL ARCHITECTURE (HOW IT WORKS)
- Frontend calls backend REST APIs using Axios.
- JWT token stored in localStorage.
- Axios default header is set in AuthContext:
  - api.defaults.headers.common['Authorization'] = `Bearer ${token}`
- Backend verifies JWT in middleware `authenticateToken`.
- MongoDB stores Users, Communities, Discussions, Resources, Notifications, Messages.
- Socket.IO server runs with Express server, used for:
  - user-specific rooms (user_<userId>) for private messages
  - conversation rooms (conversation_<id>)
  - community rooms (community-<communityId>)

5) MAIN FEATURES (WHAT TO DEMO)
- Authentication
  - Register / Login
  - Forgot password + reset password (token)
  - Optional email verification (auto-verified if email not configured)
- Communities
  - Create community (category, rules, tags, private/public)
  - Membership model (members array with roles)
  - Invitations + join requests
- Discussions
  - Create discussions inside a community
  - Attachments supported (images/docs)
  - Replies, likes, views, pinned/locked flags
- Resources

  - Types: article/video/document (file upload) or link
  - Like + comment + download tracking
  - Access control: membership required (admin bypass)
- Notifications
  - Unread count, mark read, mark all read, delete
  - Handles join requests / invitations actions from UI
- Messages (Real-time Chat)
  - Send message with optional attachment
  - Conversations list + unread count
  - Read receipts + typing indicators (Socket events)
  - Soft delete per user and full delete when both deleted
- Admin Dashboard
  - Admin-only routes
  - Platform stats: user/community counts, discussions/resources totals
  - User management endpoints with pagination/filtering

6) IMPORTANT BACKEND ENTRY POINTS (MENTION IN INTERVIEW)
- `backend/server.js`
  - Express app setup + security middleware
  - MongoDB connection using Mongoose
  - Registers routes:
    - /api/auth
    - /api/users
    - /api/communities
    - /api/discussions
    - /api/resources
    - /api/notifications
    - /api/messages
    - /api/admin
  - Creates Socket.IO server and listens for events
- `backend/middleware/auth.js`
  - `authenticateToken`: verifies JWT, fetches user, checks active
  - `requireAdmin` / `requireModerator`: role-based access

7) IMPORTANT FRONTEND ENTRY POINTS
- `frontend/src/App.js`
  - React Router routes
  - `ProtectedRoute` used for private pages and `adminOnly`
- `frontend/src/contexts/AuthContext.js`
  - manages token/user state
  - calls `/api/auth/me` on refresh to restore session
- `frontend/src/contexts/NotificationContext.js`
  - fetch notifications, unread count
  - perform actions like accept invite / approve join request

8) DATA MODEL (SCHEMA QUICK EXPLANATION)
- User
  - username, email, hashed password
  - role: user/moderator/admin
  - communities[], notificationSettings, online status
- Community
  - creator, moderators, members[{user, role}]
  - invitations[], joinRequests[], rules[], settings
  - stats: memberCount/discussionCount/resourceCount
- Discussion
  - author, community, title/content, attachments
  - replies[] (nested subdocs), likes[], views[]
- Resource
  - author, community, type (file/link), tags/category
  - likes[], downloads[], comments[]
- Message
  - sender/recipient, content, attachment, isRead
  - conversationId generated by sorting two user IDs
- Notification
  - recipient/sender, type, title/message
  - relatedEntity + actionUrl

9) SECURITY / BEST PRACTICES TO HIGHLIGHT
- Password hashing with bcrypt (pre-save hook)
- JWT expiry (default 7d), token validation + user active check
- Protected routes on frontend + protected APIs on backend
- Input validation via express-validator
- Helmet headers + rate limiting
- Access control examples:
  - Admin-only endpoints under /api/admin
  - Resources restricted to community members (unless admin)

10) REAL-TIME FLOW (EXPLAIN LIKE A SYSTEM DESIGN)
- Client connects to Socket.IO.
- After login, client emits `join-user-room` with userId.
- When user sends message:
  - POST /api/messages (saves in DB)
  - server emits `newMessage` to recipient room `user_<recipientId>`
- Online status:
  - on join-user-room => user isOnline=true
  - on disconnect => user isOnline=false

11) COMMON INTERVIEW QUESTIONS (WITH SHORT ANSWERS)
- Why JWT vs sessions?
  - JWT is stateless, easy to scale horizontally, works well with SPA.
- How do you secure APIs?
  - auth middleware, role checks, validation, rate limiting.
- How do you handle file uploads?
  - Multer stores files in server uploads folder; DB stores metadata/path.
- How to scale chat?
  - Use Redis adapter for Socket.IO, store messages in DB, load by conversationId.
- How do you ensure conversationId is consistent?
  - Sort the two user IDs and join them to generate stable conversationId.
